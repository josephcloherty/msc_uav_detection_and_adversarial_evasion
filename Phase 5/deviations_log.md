# Deviations log

**21 July 2026. Network topology fixed to the scenario, not to the run seed.**

Decision. The gNB count, positions, height, carrier frequency and UE region size are properties of the scenario name and are identical across every replicate of that scenario. Sites are placed deterministically as a centre cell plus a hexagonal ring at the configured inter site distance. The seed varies only initial UE placement, the number of aerial UEs, mobility, traffic jitter, per link LOS and shadow fading draws, channel seeds and measurement error.

Reason. The dataset is meant to support a classifier that separates aerial from terrestrial UEs within a deployment, not one that separates deployments. Letting the topology move with the seed would put a per run confound into every geometric feature, since visible gNB count, neighbour SINR spread and handover rate all respond directly to site density. Holding the deployment constant makes each seed a genuine replicate of the same observation problem, and keeping the three named scenarios as separate fixed topologies preserves the UMa, RMa and UMi comparison the earlier phases were built around.

**21 July 2026. Scenario generation draws from a dedicated Philox stream.**

Decision. phase5_ScenarioGen resolves every stochastic quantity before the simulation starts, drawing from a RandStream of generator type Philox seeded from the run seed, and writes the results into the run configuration as fixed numbers. createScenarioChannels keeps its Threefry stream for LOS and shadow fading, and the simulator continues to run off the global stream seeded by rng.

Reason. Three consumers share one seed value, so they must not share one sequence. Different generator types guarantee independent sequences without an arbitrary seed offset convention that later work could accidentally collide with. Resolving the draws before the run also means the traffic sources are built from fixed scalars rather than sampling at run time, which is what preserves the byte reproducibility contract inherited from Phase 3.

**21 July 2026. Aerial population randomised per run; swarm command and control modelling descoped.**

Decision. The number of aerial UEs is drawn per run rather than fixed. A configurable probability decides whether a run is single aerial or multi aerial, and a multi aerial run draws its group size uniformly from a configurable range, defaulting to a roughly even split of the two cases with group sizes of two to six. Every aerial UE in a multi aerial run receives independent placement, mobility and traffic draws, with no leader and follower role differentiation. The parameters are global rather than per scenario, but sit in their own configuration block so they can be split per scenario later without rework.

Reason. A dataset in which every positive example is a lone aerial UE would let a classifier key on the count of unusual UEs rather than on the per UE signature, and would not represent the multi drone case the threat model anticipates. Role differentiation was considered for D5.1 and deliberately left out of scope: distinguishing a leader from followers requires a command and control relay traffic model and an inter UE link at the simulator layer, neither of which the Fudan scaffold or the toolbox provides, so the distinction could only have been asserted through the label rather than realised in the observables. That would put ground truth into the simulation that the network could not see, which the non cooperative threat model forbids. Independent draws give a defensible multi aerial case now, and swarm command and control modelling is recorded as possible future work for a later deliverable if time allows.

**21 July 2026. Per UE traffic jitter replaces the class identical sources.**

Decision. Traffic specifications are generated per UE rather than per class. The Phase 4 class profiles remain the central values, and each UE's data rate and its finite on and off times are scaled by factors drawn once from the seeded scenario stream, then frozen as fixed scalars in the run configuration. The jitter fractions are configurable and setting them to zero restores the Phase 4 behaviour exactly.

Reason. Identical sources within a class make the traffic features almost noiseless, so a classifier trained on the resulting dataset would learn a threshold that no real network could reproduce and the Phase 7 evasion cost would be measured against an unrealistically sharp boundary. Jitter widens the within class distribution without changing the between class contrast that Phase 4 established. Freezing the drawn values before the run keeps every source deterministic, so the reproducibility contract is unaffected.

**21 July 2026. Replay written to disk rather than displayed, and the pipeline made headless.**

Decision. phase5_Pipeline removes the waitbar and the interactive replay call. Position logs, node objects, handover managers and the scenario configuration are written instead to one replay bundle per run, in the same structure the viewer's own save button produces, and reopened afterwards with phase5_ReplayRun or by passing the path to replayScenario. The position log is stored un culled so the file stays independent of the settle and cull settings in force when it was generated.

Reason. Batch runs execute on parallel workers with no display, so a figure or a waitbar would either fail or block. Writing the bundle keeps the replay available for every run rather than only for runs launched interactively, which matters because a batch of tens of runs is precisely the case where a single anomalous run needs inspecting after the fact.

**21 July 2026. Progress reporting moved from the pipeline to the batch client.**

Decision. The waitbar that phase3_Pipeline and phase4_Pipeline drew from inside the run was removed. Each worker instead sends its own simulated-time fraction to a parallel.pool.DataQueue at a configurable rate, and phase5_Progress renders the messages on the client. The default display is one horizontal bar per run in a single window, coloured by state and labelled with the run name, percentage and state, with the aggregate on a header line; batches larger than a configurable limit fall back to a single aggregate waitbar and sessions without a desktop to throttled text. Overall progress is the mean simulated-time fraction across the runs being executed, with skipped runs excluded from the denominator, and the progress queue is stripped from the configuration before the replay bundle is written.

Reason. A worker cannot draw a figure of its own, so all rendering has to happen on the client from reported state. A purely aggregate readout was tried first and rejected: with eight runs in flight it gives no way to tell a slow run from a stalled one, or to see that a particular scenario is the one failing, which is exactly what a long batch needs to be diagnosed without waiting for it to end. Drawing every run as a bar in one axes costs two property assignments per redraw regardless of the run count, so the per-run view is no more expensive than the aggregate one, and the bar limit exists only because the labels stop being legible rather than for any performance reason. Reporting completed runs alone was rejected for a separate reason: a batch of thirty second simulations at roughly real time would show nothing but zero per cent, with no estimated time remaining, until the first worker returned, which is the interval during which the estimate is most wanted. Excluding skipped runs stops a resumed batch reporting itself as nearly complete before it has done any work. The queue is a live parallel object with no meaning after the batch, so writing it into an archived replay would at best be noise and at worst unloadable.

**21 July 2026. Parallel Computing Toolbox treated as a hard requirement.**

Decision. phase5_RunBatch checks for the toolbox licence and installation and raises an error if either is missing, naming the single run route through phase5_Pipeline as the alternative. It does not fall back to a serial loop.

Reason. A silent fall back turns a licensing problem into an apparent hang: a batch sized for eight workers takes eight times as long with no indication of why. Failing at the outset with a named cause is recoverable in seconds, and the single run route remains available for machines without the toolbox.

**21 July 2026. SRS capacity checked against the total UE count, not the anchored count.**

Decision. The generator asserts that the total number of UEs in a run does not exceed the configured sixteen UE per gNB SRS limit, before any simulation object is created. A manual periodicity override is exposed in the configuration and, when set, is applied through an explicit SRS configuration on every connection, with failure rethrown naming the constraint.

Reason. configureULforSRS gives every UE a dedicated uplink link to every gNB so that all cells receive its SRS, so the per gNB UE count equals the total UE count rather than the count anchored to that cell. Reading the constraint as a per cell limit would allow populations that fail inside connectUE partway through a batch. Checking on the client before the pool starts turns that into an immediate and actionable error. The override branch is untested until first use and any use of it must be recorded here, as the plan requires.

**21 July 2026. Scheduler-log RNTI taken from the anchor gNB connection table, not from the node ID.**

Decision. The RNTI used to find a UE in the scheduler context and grant logs is now read from the anchor gNB's own connection table, matching the UE node identifier against UENodeIDs and taking the corresponding entry of ConnectedUEs. The node-derived UE identifier plus cfg.rntiOffset is retained unchanged for the SRS path, where it is correct. The pipeline asserts that both properties exist and that each UE appears in its anchor's table, rather than falling back to an offset.

Reason. The first end-to-end Phase 5 run produced an entirely empty CQI and MCS block in all three scenarios. phase5_SchedulerDiag established that the two identifiers are different quantities: SRS events carry a node-derived RNTI, empirically the node identifier less two, while the scheduler carries the UE's connection index at that gNB, counted in attachment order and unrelated to node numbering. At two gNBs a diagnostic run showed gNB 1 holding nodes 3 and 5 as RNTI 1 and 2, so of three UEs only one resolved correctly under the node-derived convention; at five or seven gNBs the expected values exceed the largest RNTI any gNB ever issues, nothing matches, and every CQI and MCS column is NaN. No constant offset can repair this, because the correct value depends on attachment order rather than on node numbering, which is why the mapping is now read from the toolbox rather than calibrated. The same fault is latent in phase4_Pipeline, whose CQI and MCS columns were never generated; the Phase 4 folder has been left untouched and the point is recorded here.

Note also that the Phase 4 C2 item, the DL CQI field path inside snapshotContext, is confirmed resolved: the diagnostic logged a non-NaN wideband CQI and a non-NaN uplink MCS estimate on every one of 694 context rows. The recursive field probe written for it works on R2024b.

**22 July 2026. Resumable checkpointing by segmented incremental CSV, salvage default, no live continuation.**

Decision. When cfg.checkpoint.enable is set, each run advances the simulation in segments of cfg.checkpoint.everySimSeconds simulated seconds, default five, and rewrites its feature CSV from the accumulated logs after every segment; a marker file beside the CSV records the simulated time reached and a completion flag. On resume the batch skips runs marked complete, and an interrupted run is either accepted with its salvaged rows and marked done, cfg.checkpoint.resumeMode "salvage", the default, or cleared and rerun from scratch, "restart". True mid simulation continuation from a saved state is deliberately not implemented.

Reason. A single run is long enough that a nightly shutdown cuts one off partway, which was losing whole runs. The rows are salvageable because every finished ten second window is a self contained row, so rewriting the CSV after each segment costs almost nothing against the simulation and bounds the loss to the segment in progress. Live continuation of the same simulation was investigated and rejected: wirelessNetworkSimulator is a singleton with live event scheduling, and the handover managers and schedulers hold addlistener connections and scheduled actions that do not survive being saved and reloaded into a runnable state. A resume that reloaded a broken object graph would fail silently, producing plausible but wrong rows, which is the worst outcome for a training set, so it is not offered. Salvage is the default rather than restart because it makes forward progress every night and cannot loop, whereas a machine that shuts down at a fixed wall clock hour would never complete a restarted run; a run that must be full length should be shortened through cfg.window.simulationTime so it finishes in one sitting. The marker write is atomic, a temporary file renamed into place, so an interruption during the write cannot leave a marker that misreports completion.

**22 July 2026. Progress reporting resolution raised to half a per cent per run.**

Decision. cfg.progress.updatesPerRun was raised from fifty to two hundred, so each run reports its simulated time fraction every half per cent rather than every two per cent, and salvaged runs are drawn in their own colour in the per run window.

Reason. Each message is one send from a worker to the client, cheap at this pool size, and the finer resolution gives a smoother bar over a run measured in hours where two per cent steps are a long wait between visible movement.

**21 July 2026. RNTI conventions resolved and checked once per run rather than calibrated once per phase.**

Decision. Every run now resolves and validates both identifiers before and during execution. phase5_ResolveRNTI derives the scheduler RNTI from the anchor gNB connection tables and asserts, before the simulation starts, that the tables exist, that each UE appears in its anchor's table exactly once, and that no two UEs on the same anchor collide; it prints the per-UE map of node ID, class, anchor gNB, scheduler RNTI and SRS RNTI. rntiVerifier then checks the SRS offset in flight against the RNTIs actually carried by SRS reception events, in a one-shot check at the settle time, and either passes, aborts naming the offset that would work, or corrects the managers in place when cfg.measurement.autoCorrectRNTI is set. The listener is deleted the moment the check fires.

Reason. Phases 2 and 3 calibrated the offset by hand and carried the number forward, which is precisely how a value correct for a three-cell layout came to be used unchallenged at five and seven. The two identifiers are also not the same quantity and only one of them is an offset at all: the scheduler RNTI is a connection index and is now derived rather than calibrated, so it cannot drift; the SRS RNTI genuinely is node derived and remains empirical, so it is the one that needs checking. A wrong SRS offset fails silently rather than loudly, since the managers simply ingest nothing and the run completes with a full CSV of NaN SINR columns; at the measured cost that is hours of compute lost with no error raised. Checking at the settle time bounds the loss to seconds of simulated time and keeps the check window inside the span the extraction discards, so nothing in the dataset is computed from measurements taken under an unverified identifier. Auto-correction defaults off, matching the pipeline's general preference for a loud failure over a silent repair, and is provided because losing a thirteen hour unattended run to a recalibratable constant is the worse outcome for a long batch.

**21 July 2026. Site count reduced to five and run length extended to 60.5 s on measured cost.**

Decision. All three scenarios drop from seven sites to five, and the run length rises from 30.5 s to 60.5 s with the 10 s window, 1 s stride and 0.5 s settle unchanged. A cost model calibrated from the measured runs was added to the configuration and phase5_DryRun projects the batch wall time before launch.

Reason. The first smoke runs measured 1881 s of wall time for six simulated seconds at seven gNBs and three UEs, 314 times slower than real time. Cost is dominated by per packet channel filtering across the UE to gNB links and by every UE's SRS being received at every gNB, so it scales with the product of simulated time, gNB count and UE count; the original settings projected to 9.3 hours per run and 186 CPU hours for a twenty run batch, which is not a schedule that survives a re-run. Feature rows scale with UE count and with the simulated time less the fixed settle and first window, so UE count cancels in the cost per row and only the site count and the warm up fraction are worth attacking. Five sites remains inside the five to seven gNBs D5.1 specifies, so this is a settings change rather than a departure from the plan, and the longer run amortises the fixed 10.5 s of warm up over fifty one windows instead of twenty. Together they take the cost from 42.2 to 24.6 hours per thousand rows. The reduction in site count does slightly compress the visible gNB count, which is one of the stronger aerial features, and that is accepted knowingly: the smoke rows show the aerial UE at the full site count and terrestrial UEs at one to three, so the contrast survives five sites.

**21 July 2026. Ring sites spaced evenly rather than on a fixed sixty degree grid.**

Decision. The gNB ring positions are spaced evenly over 360 degrees by the number of ring sites, so six ring sites give a hexagon, four give a cross and five a pentagon. The topology field was renamed from inter site distance to site radius.

Reason. The first implementation took the first N angles of a fixed sixty degree grid, which is correct only when the ring is full. Reducing the deployment to five sites exposed it: four ring sites landed at 0, 60, 120 and 180 degrees, leaving the entire 240 to 300 degree sector without a site, so every UE placed there would have seen an unrepresentative cell count and the visible gNB feature would have carried a purely geometric artefact of the layout code. The rename reflects what the parameter always controlled, the centre to ring distance, which equals the inter site distance only for a full hexagonal ring.

**21 July 2026. Mobility chain parameters exposed in the configuration.**

Decision. The TR 36.777 Table A.2.1-1 handover parameters held as handoverManager defaults are restated in the configuration and pushed onto each manager after construction, with an assertion that every configured field names a real property. The scan period and scan start time are excluded and explicitly rejected if supplied.

Reason. The whole data pipeline is meant to be adjustable from one file, and the mobility chain determines the handover features directly, so leaving it reachable only by editing the class would have made the configuration incomplete in exactly the place it matters most. The defaults reproduce the class values, so the change is inert unless used. The two excluded fields are read by the constructor when it schedules the periodic scan, so a value set afterwards would be accepted and silently ignored; rejecting them is more honest than offering a parameter that does nothing.

**21 July 2026. addMobility bounds convention verified against recorded trajectories.**

Decision. The four element Bounds vector passed to addMobility is treated as centre x, centre y, width and height. The interpretation is exposed as a configuration option so the alternative lower left corner reading can be selected without a code change.

Reason. The convention was not documented in the Phase 2 to Phase 4 scripts beyond an inline comment, and the two readings place the UE region in different parts of the plane, which would silently move every UE relative to the sites. It was resolved by checking the recorded Phase 3 UMa trajectories against both readings: the aerial UEs reached coordinates that only the centre reading permits. Making it configurable means a toolbox behaviour change is absorbed in the configuration rather than found again by inspection.

**21 July 2026. Output directory resolved in the generator.**

Decision. An empty output directory in the configuration is resolved to the Phase 5 data folder by phase5_ScenarioGen, and the resolved path is written into every run configuration.

Reason. writeFeatureCSV falls back to a path relative to its own file location, which was correct while it sat directly under core but now resolves one folder too deep. Resolving centrally means the CSV, the replay bundle and the manifest are guaranteed to land together, including when a single run is driven directly rather than through the batch runner.

**21 July 2026. UMi promoted into the batch scenario cycle, behind a smoke check.**

Decision. The batch cycles UMa, RMa and UMi at equal weight rather than the UMa and RMa pair the earlier phases used. phase5_SmokeCheck runs one short simulation per scenario through the real pipeline first and checks the resulting CSV for schema match, both class labels, finite serving SINR, more than one visible gNB, a populated CQI column and non zero uplink traffic. It writes to data/smoke with a shorter window than the dataset uses, and phase5_MergeDataset globs the dataset folder non recursively, so smoke rows cannot reach the dataset.

Reason. UMi was previously optional and was left at Phase 3 level, so it has never been run through the Phase 4 measurement and traffic stack and Phase 5 is its first exposure to the CQI logging scheduler and the per class traffic sources. It also takes a different code path from the other two forks, supplying its own aerial channel builder because UMi-AV Alternative 1 is not CDL-D based. Including it widens the deployment coverage of the dataset, which is worth having for the classifier's generalisation argument, but the combination of an unexercised fork and a long unattended batch is where a column of NaNs goes unnoticed. Verifying each scenario end to end in a few minutes first is cheaper than discovering the problem after the batch. Note that lengthening the cycle changes which scenario a given seed index maps to, so a seed range run under the earlier two way cycle produces a different set of runs; existing files are unaffected because the run identity is the scenario and seed pair.

**21 July 2026. Feature schema held at the Phase 4 column set for D5.1.**

Decision. Phase 5 asserts and writes the Phase 4 schema unchanged. The spatial clustering and RRC event proxy columns belong to D5.3 and will be appended to the same locked list when that deliverable is implemented.

Reason. D5.1 is the generator and batch runner, not a feature change. Keeping the column set fixed means the Phase 5 CSVs concatenate with the Phase 4 files and any run produced now stays valid after D5.3 appends, since appended columns leave earlier files as an exact column prefix.

**21 July 2026. Run diagnostics replaced by a batch manifest.**

Decision. exportRunDiagnostics was not carried into Phase 5. Provenance is recorded instead in one manifest row per run, holding the scenario, seed, topology parameters, population figures, windowing settings, shadow fading state, jitter fraction, row count, handover and ping pong totals, wall time, MATLAB release and output paths.

Reason. The per run diagnostics file was built for inspecting single runs in detail and writes a large binary artefact per run, which does not scale to a batch. The manifest holds what reproduction actually needs in one text file that can be joined back onto the dataset on the scenario and seed columns, and the replay bundle remains available for any run that needs detailed inspection. The diagnostics exporter is unchanged and still available in the Phase 4 folder.

**26 July 2026. Checkpointing moved from segmented run calls to a scheduled action.**

Decision. The feature CSV is rewritten from a periodic action scheduled on the simulator inside one run call, rather than by advancing the simulation in segments with repeated run calls.

Reason. Multi step running, run with IsLastStep false, was introduced in R2026a; this project runs R2024b, where the simulator is torn down when run returns and a second call raises the init error. The segmented loop was also passing the cumulative segment end into an argument documented as a duration, so it would have overrun the configured run length even on a release that supports the call. A scheduled action needs one run call, uses the same mechanism as the traffic sampler, position recorder and progress reporter, and gives the same interruption guarantee. The checkpoint interval remains configurable in simulated seconds, and no CSV is written before settleTime plus windowLen so that no clipped window, computed over a shorter duration than every other row, can reach the dataset.

**26 July 2026. Salvage records the simulated time actually reached, and flags the run truncated.**

Decision. Closing out an interrupted run keeps its true simReached in the marker and sets a derived truncated flag, which is computed inside phase5_Checkpoint from the reached time against the configured length rather than passed in by the caller. The flag is reported per row in the manifest as simReached_s and truncated, skipped runs are described from their markers rather than left as NaN, and the batch names truncated runs instead of counting them as complete on disk.

Reason. The previous implementation wrote simReached equal to simulationTime on salvage. That made a run cut off at five seconds of 60.5 indistinguishable from a full one and unrecoverable, because every later batch read complete and skipped it: a batch reported itself finished in one second against six runs holding a twelfth of their intended length. Salvage is still the default resume mode, for the reasons recorded on 21 July, but it is now a recorded shortening of a run rather than a silent one, and phase5_RepairCheckpoints exists to undo it. That helper measures each run from the largest winEnd_s in its feature CSV rather than trusting the marker, since the markers already on disk were the thing that was wrong, and its clear action archives rather than deletes so a superseded run stays available for comparison.

**28 July 2026. Cost model taken from measurements on disk rather than from the configured constant.**

Decision. phase5_CostModel keeps one row per completed run in data/costmodel_measured.csv, with the pool size it was measured at, and returns the median of the rows matching the pool size in question. The dry run projection, the pre batch estimate and the live ETA all use that in preference to cfg.batch.costModel, which is now only the prior for a machine with no measurements. The prior itself was updated from 14.9 to the measured 33.6.

Reason. The constant was calibrated from six second smoke runs and understated the first full batch by more than a factor of two, because fixed per run overhead dominates a six second run and the per window extraction cost grows with the logs. An estimate that a batch is 79 CPU hours when it is 190 is worse than no estimate, since it is acted on. Pool size is recorded with each measurement because the constant is measured under contention and a value from six workers does not transfer to twelve on the same machine; where no matching measurement exists the fallback is reported as a lower bound rather than presented as a like for like figure.

**28 July 2026. Estimated time remaining computed per run and rescaled continuously, not extrapolated from the mean percentage.**

Decision. Workers report their own wall time with each progress message, at one message per per cent of a run. The client keeps a per run rate as an exponentially weighted mean of simulated fraction per worker second and shows each run's own ETA on its bar; the cost model is rescaled by the weighted ratio of observed to predicted cost across the reporting runs, so runs not yet started are estimated from the machine's current behaviour; and the batch estimate places the pending runs on the workers as they free up, longest first. The previous mean percentage extrapolation is retained only as the fallback when nothing has reported and no cost model was supplied.

Reason. The extrapolation is correct only when every run is in flight at once. With twelve runs on six workers the six that have not started count as zero per cent rather than as a full run of work each, so the batch is reported as finishing at about half the true time, and the error is largest at the start of a batch, which is exactly when the number is used to decide whether to leave the machine running. A per run rate measured on the worker also excludes queue latency and the time a run spent waiting for a worker, neither of which is part of that run's cost.

**28 July 2026. Parallel pool startup retried and degraded rather than fatal.**

Decision. phase5_RunBatch opens the pool through a helper that reuses an open pool, clears the half opened pool and stale cluster jobs on failure, retries a configurable number of times with a pause, and then halves the worker count until a pool opens, reporting any reduction. It raises the profile's worker ceiling when the request exceeds it, warns once when the request exceeds the physical core count, and on total failure raises an error naming the causes to check in order.

Reason. The twelve worker launch on 28 July failed with a timeout opening localhost:27370, a pool handshake failure caused by the environment rather than by the batch: orphaned worker processes holding the port, loopback blocked by security software, stale job metadata, or too many handshakes for a loaded machine. Aborting on it loses a night of an overnight batch for a condition that a retry or a smaller pool usually clears, and the batch is resumable in any case, so the conservative behaviour is to get some runs started. The worker count reduction is printed because pool size affects the measured cost constant and therefore must be traceable from the manifest.

**28 July 2026. Checkpointing removed.**

Decision. The pipeline runs the whole simulation in one call and writes its feature CSV once, from the completed logs. The resume classification, the salvage and restart branches, the per run marker helper and the repair tool are removed from the code path and kept, unreferenced and off the MATLAB path, under removed_checkpointing_20260728 with a note on reinstating them. A run whose CSV exists is complete; a run that did not finish leaves nothing behind and is enumerated again. The manifest retains simReached_s and truncated.

Reason. Checkpointing existed solely to survive an overnight machine shutdown, and that cause has been dealt with at the machine. Its cost was not zero: it introduced the segmented run that killed the first batch, and then a salvage path that silently accepted six runs at a twelfth of their length. With whole runs as the unit of work the failure mode is losing one run's hours rather than corrupting the dataset with short runs, and re-running the batch completes it because finished runs are skipped. The manifest columns stay because phase5_CostModel divides wall time by the simulated seconds actually run, and because dropping columns would break the column prefix relationship with the manifests already written.

**28 July 2026. Pool port range moved with pctconfig before any reduction in workers.**

Decision. phase5_RunBatch sets the client listening port range through pctconfig and tries each of a configurable list of ranges, cfg.batch.poolPortRanges, before retrying and before reducing the worker count. The defaults are the session's own setting, then ephemeral ports, then 40000-41000 and 21000-22000. The range that succeeds is reported with the pctconfig line to add to startup.m.

Reason. The Processes profile validation passed every job stage, including a communicating job on twelve workers, and failed only the interactive pool stage, at the client's bind of localhost:27370. That combination localises the fault to the machine refusing that port, and on Windows the usual cause is a reserved exclusion block from Hyper-V, WSL or Docker, which makes a port unbindable even though nothing is listening on it. The previous behaviour, retrying and then halving the worker count, could not fix a blocked port and merely delayed the failure while wasting the retry budget. Ephemeral ports are included because the operating system assigns them from what is actually free, so they cannot collide with a fixed reservation at all. pctconfig does not persist between sessions, which is why the runner sets it on every launch rather than relying on a preference.

**29 July 2026. LOS state made dynamic and spatially consistent; the frozen draw is retired.**

Decision. The LOS/NLOS state used for pathloss and shadow fading is evaluated per packet from the live node positions, through a spatially consistent random field built once per run. The field follows TR 38.901 clause 7.6.3.1 Option 2: independent standard normals on a grid whose spacing is the LOS state correlation distance of Table 7.6.3.1-2, interpolated to the sampling point and mapped to a uniform variate, with the state given by comparing that variate against the Table B-1 probability at the current height and 2D distance. There is one field per gNB, so two UEs at the same place see the same state towards a given cell. Shadow fading is drawn from two further fields, at the LOS and NLOS SF correlation distances, with sigma re-read for the live state. linkState is the single entry point and is called by both the channel model and the replay renderer. cfg.channel.dynamicLOS set to false restores the previous behaviour exactly, including the per link Threefry substream order.

Reason. The state was previously drawn once, from the initial node positions, and held for the whole run. For an aerial UE at 15 to 30 m/s over a multi minute run that is plainly wrong: the underlying probability sweeps its full range as the UE crosses kilometres and changes altitude, while the state never moves. It was noticed as an apparent rendering fault in the replay, where the serving link kept one colour beside an annotation whose pLOS was visibly changing, and the renderer turned out to be reporting the simulator honestly. The magnitude of the error is scenario dependent and worth stating: in UMa-AV between 40 and 100 m the Table B-1 probability never falls below about 0.91, so freezing it cost little there, whereas UMi-AV over the same heights sweeps roughly 0.83 down to 0.20 across a cell, and terrestrial UEs span the full range, so those are where the frozen state distorted the pathloss.

A field indexed by position was chosen over a Markov chain updated in place because pathloss is evaluated per packet in whatever order the simulator delivers them. A chain carrying state between calls would make the result depend on packet ordering and break the fixed seed byte identical regeneration contract; a pure function of position cannot.

Known limitation. The interpolated field reproduces the correlation DISTANCE of Table 7.6.3.1-2 but not the exponential correlation SHAPE: its autocorrelation is about 0.95 at a fifth of the correlation distance, 0.25 at one correlation distance and zero beyond two, against the exponential's 0.37 at one. The marginal distribution is exact everywhere, which is what the threshold test actually depends on, and is enforced by dividing by the norm of the interpolation weights; phase5_ValidateLOS checks it.

Second known limitation. The per link CDL objects are still built once, from the initial geometry and the initial LOS state, so a state change alters the pathloss branch and the shadow fading sigma but not the fast fading profile. This narrows the existing static channel deviation rather than removing it. Rebuilding nrCDLChannel objects mid run was judged not worth its cost at this stage. The setup time state is now READ FROM THE FIELD rather than drawn independently, so the profile a link starts with always agrees with its initial pathloss branch.

Third known limitation. A LOS transition steps the shadow fading term, because sigma changes with the branch. That is the correct consequence of a state change rather than an artefact, but it is a discontinuity in an otherwise continuous quantity.

**29 July 2026. LOS state excluded from the feature set by design, and recorded in diagnostics instead.**

Decision. There is no LOS column in the feature CSV and there will not be one. The state is summarised per UE by losDiagnostics, carried in the run summary as losFractionMean, losTransitions and losDynamic, and stored in the replay bundle. phase6_LoadDataset refuses to load a CSV containing any column matching a LOS flag or a raw position, altitude or true speed quantity.

Reason. An operator cannot observe LOS state. It is a latent property of the propagation environment, not a reported measurement, and nothing in the RRC, NAS or MAC reporting chain carries it. It is also near collinear with the label in this scenario set, since Table B-1 gives pLOS equal to one above 100 m in UMa, so including it would leak ground truth and inflate every Phase 6 score in a way that could not be defended. The observable consequences of LOS propagation are captured instead, by the across subband CQI spread for frequency flatness, the lag one autocorrelation and fade rate of serving SINR for fading dynamics, and the rank indicator statistics for rank collapse.

**29 July 2026. Feature schema extended to the full operator observable set; the Phase 4 hold is lifted.**

Decision. phase5FeatureSchema appends fifty columns to the Phase 4 set, which remains an exact prefix. The blocks are rank and CSI structure, resource consumption, retransmission based reliability, timing advance, serving SINR dynamics, cell geometry, serving cell history, and extended traffic. The 21 July decision to hold the schema at the Phase 4 columns for D5.1 is superseded. cqiLoggingScheduler was extended to log the across subband CQI spread, timing advance and buffer occupancy in its context log, and the retransmission flag, granted layers and HARQ process in its grant log, with retransmission grants now captured through the previously uninstrumented scheduleRetransmissions hooks. handoverManager.sinrLog, written since Phase 3 and never read, is now the source of the cell crowding features.

Reason. Several of the strongest published discriminators were already sitting in the logs and being discarded: the rank indicator was written to the context log and dropped at extraction, the granted resource block count likewise, and the per cell SINR snapshot was recorded for offline plotting and never used. Others, notably retransmission rate and timing advance, were not captured at all despite being standard operator KPIs. The Phase 4 set also kept only the mean and variance of serving SINR, which discards the shape of the trajectory that a climb or descent produces. Since a regeneration of the dataset was already forced by the LOS change, extending the schema in the same pass costs one regeneration rather than two.

Known limitation, carried forward. Every scheduler derived column still follows the ANCHOR cell rather than the serving cell, under the logical handover model, so the CQI, MCS, rank, resource, reliability and timing advance blocks are weaker than their real network equivalents. This was already recorded as a Phase 4 deviation and is not made worse here, but it now applies to a much larger share of the feature set and should be stated plainly in the write up.

Known limitation. Timing advance and buffer occupancy are probed by name from the R2024b UEContext, whose layout for these quantities is not documented. Where the probe finds nothing the columns are NaN, phase5_SmokeCheck reports it, and phase6_LoadDataset drops all NaN columns with a printed note rather than imputing them to a constant.

**29 July 2026. Phase 6 predictor list derived from the CSV header rather than hard coded.**

Decision. phase6_LoadDataset removes a fixed exclusion list from the header and treats everything else as a predictor, dropping all NaN and constant columns with a note. It asserts that no non observable column is present.

Reason. The list of twenty predictor names was written out by hand, so any column added upstream was silently ignored and the models would have kept training on the Phase 4 subset while the schema grew underneath them. Deriving the list removes that failure mode; the assertion is what keeps the derivation safe, since a derived list would otherwise happily absorb a leaking column.

**29 July 2026. UEContext probes made container agnostic and rate limited.**

Decision. The name based probes normalise struct, object and table levels through one members_ helper before walking them, and run only during an opening window of context snapshots, configurable as probeWindow and defaulting to 400, after which they are retired if nothing has been found. getProbeStatus reports the outcome and phase5_SchedulerDiag prints it. The context and grant row writers assert their width.

Reason. The first version indexed every level with s(1), which is not valid on a table, and the R2024b UEContext contains at least one table level, so the diagnostic run raised inside the timing advance probe on the first scheduled slot. Normalising the container types is the fix; retiring the probes is the second half of it, because a recursive walk of the whole context for three quantities, for every UE, on every 5 ms snapshot, is not a cost worth paying for quantities the release may not expose at all. The window is a window rather than a single snapshot because timing advance does not exist until random access has completed, so probing only at the first slot would abandon a quantity that does arrive a moment later. The width asserts exist because a probe returning a vector instead of a scalar would otherwise appear as an opaque size error deep into an unattended run rather than as a named fault.

**31 July 2026. One run dispatched per worker at a time, queue ordered longest first.**

Decision. phase5_RunBatch runs its parfor with parforOptions(pool, RangePartitionMethod fixed, SubrangeSize 1), so each dispatch is a single run and a worker takes the next queued run only when it becomes free. The queue is ordered by descending estimated cost, skipped runs first, controlled by cfg.batch.dispatchOneRunPerWorker and cfg.batch.longestFirst. The parfor loop variable is the queue position, and each result record carries its run index so the manifest stays in seed order.

Reason. parfor's default partitioning is tuned for many short iterations: it divides the range into subranges of varying size and assigns them up front, which with twenty-four thirty-hour runs on twelve workers can leave one worker holding a queued run while another has nothing to do. Longest-first ordering is the classic greedy schedule for identical workers and costs nothing here because the per-run estimate already exists for the ETA; on this batch it is the difference between an estimated 92 h and 76 h finish, against an ideal of 70 h. The queue position had to become the loop variable because parfor rejects an output indexed by anything else, which also turns the run configurations from a sliced into a broadcast variable: a few kilobytes per worker, immaterial against the run cost.

**31 July 2026. Per-run text drawn as text objects, not y tick labels.**

Decision. The per-run progress window draws one text object per run, in data coordinates, in a region of the axes reserved to the left of the bars, and sets no y tick labels at all. Each row also has a full-width track behind its progress bar. The axes limits and the empty y tick vector are re-asserted after every bar data update.

Reason. With twenty-four runs the tick label approach failed visibly: the window showed four labels, for the first four runs, spread down a blank axis. Updating a Bar object returns the ruler to automatic tick mode, so twenty-four supplied labels were recycled onto four automatic ticks. Tick labels belong to the ruler and are matched to whatever ticks exist, which makes them unsafe for a per-row readout whose row count is not under the axes' control. Text objects have their own data coordinates, cannot be thinned or recycled, stay aligned with their bars if the axes rescales, and cost nothing to update at this scale. The track was added because a queued run at zero per cent otherwise draws nothing, so half of a batch larger than the pool appeared as blank space.

**7 August 2026. Per-run provenance written by the worker; manifest rebuildable from disk.**

Decision. Each run writes a one-row runinfo sidecar beside its feature CSV as soon as it finishes, from the worker that ran it, holding only the fields that cannot be regenerated: row and column counts, handover and ping-pong totals, wall time, pool size, release, output paths. phase5_RebuildManifest reconstructs a full manifest from the CSVs on disk by regenerating each run's configuration through phase5_ScenarioGen and merging the sidecar where one exists, writing manifest_rebuilt_<stamp>.csv and never overwriting a manifest a batch produced.

Reason. The manifest is built on the client from the summaries the workers return and written when the batch returns, so any client-side failure loses the provenance record for every run in the batch even though the runs are intact. On 6 August MATLAB's web GUI render process was killed out of memory with twenty-three of twenty-four runs finished, and that is exactly what happened. Because the generation parameters are deterministic in the scenario and seed pair, the only genuinely perishable information is the run's own execution measurements, so those are the only things the sidecar has to persist. The rebuild is a separate implementation from the runner's manifest builder on purpose: its job is to recover runs made by earlier versions of the runner, which a shared builder would not survive.

**7 August 2026. Batches run headless; the progress window is no longer load-bearing.**

Decision. run_batch_headless.cmd runs the batch under matlab -batch with a log file, and a plain-text status board is written to data/batch_status.txt on every redraw in every display mode. The progress window rewrites only the rows whose text has changed and redraws at most every five seconds instead of every half second.

Reason. The MATLAB desktop and all uifigure content are rendered by one Chromium process, and that process was killed out of memory during a three day batch, taking MATLAB and the batch with it. Under matlab -batch the process does not exist, so the failure cannot occur and its memory is available to the workers. The window remains available for attended runs, but it is now cheap: every graphics property set is a message into that process, and on a batch where most runs are unchanged between redraws almost all of those messages were redundant. The status file exists so that removing the window does not remove the ability to watch a batch.

**7 August 2026. Pool held at one worker per core.**

Decision. cfg.batch.numWorkers stays at 12 rather than rising to 24 to give each of a 24 run batch its own worker.

Reason. Measured cost is 33.3 s per (simulated second x gNB x UE) at six workers and 39.2 at twelve, so doubling the pool from six cost eighteen per cent per run and nearly doubled throughput: about twelve cores are usable. A further doubling to twenty-four would put two workers on each core, which cannot increase throughput, roughly doubles the wall time of every individual run, and doubles the number of full simulations held in memory simultaneously. Memory is the constraint that failed on 6 August, so the pool is sized to the cores and the surplus runs queue instead.
