# 20 July 2026

## Logbook

- Created the Phase 4 folder as a copy of Phase 3 with the run artefacts excluded: saved replay and diagnostics .mat files, generated feature CSVs, and the Phase 3 logbook and deviations log were not carried over, while all code, tools and the 3GPP source documents were. The Phase 3 originals are untouched, so the Phase 3 baseline remains reproducible in place.
- Implemented the D4.1 CQI/MCS logging route: cqiLoggingScheduler is a standalone nrScheduler subclass plugged into each gNB with configureScheduler before any UE connects. Both protected scheduling methods delegate to the base class, so scheduling decisions are those of the stock scheduler and Phase 3 radio behaviour is preserved; the subclass only records a per-UE context snapshot (wideband DL CQI, rank indicator, and the gNB's SRS-derived uplink MCS estimate) at most every 5 ms plus one row per grant (direction, MCS index, RB count). The UE-reported CQI and the gNB-side uplink estimate are kept separable in the logs for the adversarial framing.
- Wrote phase4SchedulerCheck.m as the gate for first use on R2024b, since the no-native-CQI-logging conclusion was reached against R2026a documentation: it checks the release, re-checks the public statistics() trees for native CQI/MCS series, confirms configureScheduler accepts the subclass, runs a 2 s probe and validates delegation, CQI range 0 to 15 and MCS range 0 to 28 per TS 38.214, the RNTI convention shared with the handover managers, and mid-run statistics() access for the traffic sampler.
- Implemented the D4.1 per-class traffic sources: the aerial UEs carry a steady 4 Mbps uplink video stream (within the 2 to 6 Mbps range reported in the LTE UAV measurement literature) plus the TR 36.777 command and control model on the downlink, verified against the source document (60 to 100 kbps, 1250 byte packets every 100 ms; 100 kbps at 1250 bytes reproduces the period exactly). Terrestrial UEs carry a downlink-heavy bursty profile. All On and Off periods are fixed scalars so the sources stay deterministic and seed-reproducible. A trafficSampler class records cumulative per-UE MAC and App byte counters every 0.1 s.
- Implemented D4.2: phase4FeatureSchema appends twelve columns to the Phase 3 schema (CQI mean, variance and trend; DL and UL granted MCS moments; UL and DL volume, DL/UL asymmetry, burstiness as coefficient of variation, and mean throughput), obtained by calling phase3FeatureSchema so the Phase 3 columns remain an exact prefix. extractWindowedFeatures now consumes the scheduler logs and traffic samples alongside the Phase 3 inputs with the windowing, settle gating and determinism rules unchanged, and writeFeatureCSV asserts the Phase 4 schema with byte-identical formatting. phase4_UMa.m and phase4_RMa.m drive the new phase4_Pipeline.m; the optional UMi fork was left at Phase 3 level.

- Ran phase4SchedulerCheck.m on R2024b for the first time. Findings: configureScheduler accepts the custom subclass (B pass); the overridable methods are invoked with a different signature from the current online documentation, timeResource and frequencyAllocationBitmap ahead of schedulingInfo, fixed by varargin pass-through delegation (deviations log); the simulator default channel is SISO-only, so the probe scenario was moved to single antennas (the full pipeline is unaffected, it supplies the TR 36.777 custom channel); 1004 grants logged with MCS in range (C1 pass); scheduler-log RNTIs matched the expected convention (C3 pass); mid-run statistics() access works (C4 pass); the public statistics() trees expose no CQI or MCS series on R2024b, confirming the custom scheduler is required (A pass). C2 found the UL SRS-derived MCS estimate but no DL CQI at the assumed field path; the context probe was rewritten as a depth-limited recursive search with a layout dump on failure, re-run pending.
